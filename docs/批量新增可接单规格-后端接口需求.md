# 批量新增可接单规格：后端接口需求

## 1. 背景与目标

俱乐部管理页新增“批量新增”操作，管理员可以一次选择多个游戏规格和多个目标俱乐部，并为部分规格填写固定分润金额。当前前端只有交互预览，确认按钮尚未调用写入接口。

需要后端提供一个批量写入接口，将所选规格授权给多个俱乐部；对填写了固定分润金额的规格，同时为每个目标俱乐部创建或更新对应分润配置。

## 2. 当前前端交互

- 规格按游戏分组，可搜索游戏名/规格名，支持单选、多选及某游戏“全部规格”。
- 俱乐部列表分页展示，每页 20 家；可按俱乐部名称搜索，支持跨页多选及选择当前页。
- 每个规格可填写固定分润金额，允许小数，最小值为 0。
- 提交前至少需要选择 1 个规格、1 家俱乐部，并且至少有 1 个已选规格填写了固定分润金额。
- 未填写金额的已选规格仍需要新增可接单权限，但不提交该规格的分润变更。
- 规格和俱乐部选择均使用 ID；名称只用于界面展示。

## 3. 建议接口

建议新增管理端接口（路径可按后端路由规范调整）：

```http
POST /api/admin/clubs/specs/batch
Content-Type: application/json
```

使用一个接口同时处理规格授权和分润配置，避免前端针对每家俱乐部分别调用规格更新、分润保存接口导致请求量过大或只成功一部分。

## 4. 请求参数建议

```json
{
  "clubIds": [101, 102],
  "specs": [
    {
      "gameId": 10,
      "specId": 1001,
      "fixedProfitAmount": 25.5
    },
    {
      "gameId": 10,
      "specId": 1002
    }
  ]
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `clubIds` | `number[]` | 是 | 目标俱乐部 ID，去重后至少 1 个 |
| `specs` | `object[]` | 是 | 要新增的规格，至少 1 项 |
| `specs[].gameId` | `number` | 是 | 游戏 ID |
| `specs[].specId` | `number` | 是 | 规格 ID |
| `specs[].fixedProfitAmount` | `number` | 否 | 该规格应用于所有目标俱乐部的固定分润金额；未传表示只新增规格权限，不改该规格分润 |

前端的“全部规格”最终可以展开成明确的 `specId` 列表提交；后端无需依赖前端传入“全部”标记。请以后端游戏/规格有效性校验为准。

## 5. 建议业务规则

### 5.1 规格授权

- 对每个 `clubId × specId` 新增可接单规格权限。
- 已存在的授权建议按幂等方式处理，不重复插入，也不删除目标俱乐部的其他规格。
- `gameId` 与 `specId` 必须匹配；规格所属游戏无效、规格不存在或不可用时，应返回明确错误。

### 5.2 固定分润

当规格项包含 `fixedProfitAmount` 时，对该规格的每个目标俱乐部创建或更新分润配置，字段建议沿用现有分润模型：

```json
{
  "clubId": 101,
  "specId": 1001,
  "clubMode": "FIXED",
  "clubFixed": 25.5,
  "playerMode": "FIXED",
  "playerFixed": 0,
  "settleDays": 0
}
```

- 新分润配置的 `settleDays` 建议默认 `0`。
- 如果目标俱乐部已存在该规格分润，建议只将其分润模式/金额更新为本次固定分润，并保留原 `settleDays`。
- 未传 `fixedProfitAmount` 的规格不新增、不覆盖、不删除已有分润配置。
- 同一规格金额对所有目标俱乐部相同；如后续需要按俱乐部设置不同金额，再扩展请求结构。

以上已有配置覆盖规则需后端确认，见“待确认事项”。

### 5.3 校验

- `clubIds`、`specs` 去重并校验非空。
- `fixedProfitAmount` 必须是有限数值且 `>= 0`，精度建议最多 2 位小数。
- 建议设置单次最大俱乐部数、最大规格数及最大组合数（`clubIds.length × specs.length`），并返回明确的超限错误。
- 校验失败时返回可定位的字段/ID，不应静默跳过无效数据。

### 5.4 事务与重复提交

- 建议规格授权和分润写入在同一事务中完成：全部成功或全部回滚，避免出现权限已增加但分润未写入的半成功状态。
- 接口建议具备幂等性；同一批请求重试不应产生重复授权或重复分润记录。
- 如果业务上必须允许部分成功，响应必须逐俱乐部、逐规格返回成功/失败明细，前端才能准确提示。

## 6. 响应建议

全量成功时返回汇总：

```json
{
  "clubCount": 2,
  "specCount": 2,
  "permissionAddedCount": 3,
  "permissionExistingCount": 1,
  "profitCreatedCount": 2,
  "profitUpdatedCount": 0
}
```

字段说明：

| 字段 | 类型 | 说明 |
|---|---|---|
| `clubCount` | `number` | 本次目标俱乐部数 |
| `specCount` | `number` | 本次规格数 |
| `permissionAddedCount` | `number` | 新增的俱乐部-规格授权数 |
| `permissionExistingCount` | `number` | 原本已存在的授权数 |
| `profitCreatedCount` | `number` | 新增的分润配置数 |
| `profitUpdatedCount` | `number` | 更新的分润配置数 |

失败时沿用项目现有统一错误响应，并尽量提供稳定的错误码，例如：`INVALID_CLUB_IDS`、`INVALID_SPEC`、`INVALID_PROFIT_AMOUNT`、`BATCH_LIMIT_EXCEEDED`。

## 7. 现有接口参考

当前单项接口可作为字段和行为参考：

- `GET /api/admin/clubs`：俱乐部分页/名称筛选。
- `PUT /api/admin/clubs/{clubId}/specs`：单俱乐部可接单规格更新，body 为 `{ "specs": [...] }`。
- `PUT /api/admin/profit-configs`：保存分润配置数组，字段包括 `clubId`、`specId`、`clubMode`、`clubFixed`、`playerMode`、`playerFixed`、`settleDays`。

本次需求的关键是增加一个支持多个 `clubIds` 的合并写入能力，而不改变现有单项接口。

## 8. 验收标准

1. 一次请求可将多个规格新增到多个俱乐部。
2. 规格金额有值时，所有目标俱乐部均创建/更新对应固定分润；无金额时不改该规格已有分润。
3. 已存在的授权不会产生重复记录，也不会删除目标俱乐部其他授权规格。
4. 无效俱乐部、游戏/规格不匹配、非法金额能明确报错。
5. 写入具有事务或明确的逐项部分成功结果，前端可准确展示执行结果。
6. 返回值能区分新增/已存在授权，以及新增/更新分润的数量。

## 9. 待后端确认事项

1. 确认接口路径、请求及响应字段命名。
2. 固定分润金额覆盖已有分润时，是否保留 `settleDays`；本说明建议保留。
3. 已存在的规格授权是跳过还是更新其他接单属性；本说明建议保持现有配置不变。
4. 批量操作采用全量事务回滚，还是允许部分成功并返回逐项明细。
5. 单次请求允许的俱乐部数、规格数和组合数上限。
6. 新增授权是否允许包含停用游戏/停用规格；建议由后端校验并返回明确错误。
